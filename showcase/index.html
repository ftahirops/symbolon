The old model · standing credential

Open by default

  • A long-lived secret lives on the server and on the wire
  • Reusable: one capture = unlimited logins
  • Bearer: whoever holds it is "you", on any device
  • Phishable, keyloggable, stuffable, dumpable
  • Revocation is slow and after-the-fact
Symbolon · minted lease

Closed by default

  • No standing secret — the user mints access per session
  • Single-use — the lease dies the instant it is consumed
  • Bound — to one device, one app, one action window
  • Nothing to phish — there is no reusable secret to steal
  • Self-expiring — minutes-long window, then worthless

The login ceremony

One proof. One lease. One session.

Five steps from intent to session. Notice what never happens: no long-lived secret ever travels to your app, and your app never phones home to a central authority.

The Subject proves themselves to the Vault with a fresh biometric, PIN, or passkey. One proof = one lease — cached proofs are forbidden.

The ceremony in full · step by step

Every message, every check.

The five phases above, unrolled. Follow exactly what data crosses each boundary — and notice the two things that never happen: no long-lived secret reaches the app, and the Verifier never phones home.

Subject → Vault

Fresh local user proof

The Subject taps "log in" and proves themselves on the Vault device itself — Face ID, fingerprint, secure-element PIN, or a platform passkey with user-verification required. The proof is consumed immediately and cannot be cached or reused for a second lease.

presence_proof = biometric() · one proof ⇒ exactly one lease
Vault · internal

Generate a fresh ephemeral keypair

The Vault generates a brand-new Ed25519 keypair scoped to this single lease. The private half will go only to the Subject's own user-agent; the public half is embedded in the lease so the Verifier can later demand proof of possession.

(eph_pub, eph_priv) = ed25519_keygen() · per-lease, never reused
Vault · sign

Assemble & sign the lease

The Vault fills the lease — jti, app_id, device_id, a minutes-long not_before/not_after window, allowed_actions, optional geo_constraint, the ephemeral public key — canonicalizes it (JCS, RFC 8785) and signs with its hardware-held long-lived key. The signing key never leaves the secure enclave.

vault_signature = Ed25519_sign( hsm_key, JCS(lease) )
Vault → user-agent → Verifier

Deliver across a hostile carrier

The signed lease plus the ephemeral private key travel to the Subject's user-agent over whatever transport fits — HTTP header, QR code, or deep link. The carrier is assumed compromised; it gains nothing, because the lease is single-use, bound, and self-expiring.

carrier sees: a spent-on-use, device-bound, minutes-long token — useless to steal
Verifier · §4 steps 1–6

Parse & verify the signature

The Verifier parses the JSON, checks v == 1 and type, looks up the Vault's public key in its trusted set, re-canonicalizes the lease and verifies the Ed25519 signature. A single changed byte — anywhere — fails here. All of it offline, against a locally held key.

Ed25519_verify( vault_pub, JCS(lease − sig), vault_signature ) → must pass
Verifier · §4 steps 7–8, 10–11

Enforce every binding

App match (app_id), time window against a trusted clock (±skew ≤ 30 s), geo/ASN/IP origin if constrained, and device match (device_id). Any mismatch rejects with a precise error code and no session is created.

app ✓ · within window ✓ · origin ✓ · device ✓ — else reject
Verifier ⇄ user-agent · §4 step 12

Challenge for live possession

The Verifier issues a random 32-byte challenge. The user-agent signs it with the lease's ephemeral private key and returns the signature, which the Verifier checks against the embedded ephemeral public key. This proves the presenter actually holds the key the Vault issued — not just a copied token.

challenge = random(32) · verify( eph_pub, challenge, client_sig )
Verifier · §4 steps 9, 13

Consume the lease — atomically, durably

The jti is written to the consumed-JTI store with an atomic check-and-insert. Two concurrent verifications of the same lease can never both win. From this instant the lease is dead; any replay returns lease_replayed.

INSERT jti (PRIMARY KEY) — unique-violation ⇒ already consumed
Verifier · §4 step 14

Open a bounded session

Only now does a session exist — capped at min(max_session_ttl_sec, app policy), scoped to allowed_actions, and ideally bound to the ephemeral key (DPoP) so even the freshly minted session token can't be lifted. Destructive actions can demand a brand-new single-action lease.

SessionAuthority{ subject, app, actions, ttl } · least-privilege by default

Why breaches actually happen

Not zero-days. Credentials.

The overwhelming majority of real-world breaches are not exotic exploits. They are a leaked key, a reused password, a stolen token, a subverted pipeline — a credential that should never have existed, or should have died minutes ago. Symbolon attacks the root cause, not the symptom.

~80% of breaches involve a credential or human element

And nearly all of those trace back to the same three structural sins: plaintext / long-lived secrets, no short-lived credentials, and broken, bearer-based authentication. Remove the standing secret and a single stolen credential stops being enough on its own.

How it actually fits

The honest claim.

Symbolon is an authorization gate, not a secrets manager — and not magic. Here is exactly where it sits, what it replaces, and what it doesn't.

Symbolon does not make compromise impossible.
It makes single-point compromise insufficient.

No single ordinary compromise grants sensitive access. No long-lived secret is enough by itself. No central service sits in the hot verification path. Failure degrades closed for sensitive actions — while basic availability continues.

First-party · your own systems

Directly in the path

Your auth, session, API, sensitive actions and data gate become Symbolon-aware. Each boundary verifies a short-lived, proof-bound, action-scoped lease locally. This is where Symbolon replaces standing secrets outright.

Third-party · AWS, SaaS

In front of a broker

AWS will not verify a lease. So Symbolon sits before HashiCorp Vault / AWS STS / a credential broker: the broker issues the provider's native short-lived credential only after a valid lease. Symbolon gates issuance — it never replaces IAM.

Two planes · one rule
Control plane · may be online

The verification algorithm · spec §4

Fourteen steps, one fixed order.

A conformant Verifier runs exactly these checks, in exactly this sequence. Any failure rejects — there is no partial success, no permissive fallback. Green-edged steps are the security gates; each carries the precise error code it returns.

Fail-closed is mandatory: unknown vault, unknown signature algorithm, untrusted clock, or an unavailable replay store all reject — never "allow on error".

Scams · phishing · social engineering

There is nothing to trick out of you.

Phishing and scams work by getting a human to hand over a reusable secret. Symbolon's whole shape removes the thing the attacker is fishing for.

🪝

Credential phishing

A lookalike page begs for a password or a one-time code. But there is no password to type and no standing code to relay — login authority lives on the Vault, behind a local biometric the phishing page can never reach.

✓ no reusable secret exists to surrender
🕸️

Real-time relay (AiTM)

Adversary-in-the-middle kits proxy a live session to defeat ordinary MFA. A lease fights back on three axes: it is bound to the victim's device_id, can be pinned to a country/network via geo_constraint, and demands a live ephemeral-key challenge the proxy can't satisfy.

◑ device + geo + possession proof break the relay
🎣

Consent & approval fatigue

Scammers spam approvals hoping for one reflexive tap. Each Symbolon lease needs a deliberate, fresh proof and is scoped to one app and one action set — and a panic-lock can revoke every outstanding lease at once, system-wide, in seconds.

✓ one proof = one minutes-long, single-action lease

Anatomy of a lease

What one session looks like.

A Login Lease is a small signed JSON object. Every field is a constraint that an attacker would have to satisfy — and the signature makes all of them un-forgeable. Hover the fields.

Residual risks we don't paper over: endpoint malware present at mint time can ride that window; the policy engine and any field-level encryption are separate systems whose wins aren't Symbolon's; and a lone invocable signing key stays catastrophic until co-signing ships. The win is structural — single-point compromise becomes insufficient — not a guarantee against everything.

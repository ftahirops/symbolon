# Symbolon Protocol — v0.1 (DRAFT)

**Status:** Draft. Not frozen. Breaking changes expected before v1.0.
**Codename:** Symbolon (working title — final name TBD before public release).
**Document type:** Protocol specification, RFC-style.
**Audience:** Implementers of Symbolon vaults, Symbolon verifiers, and SDK authors.

---

## 1. Introduction

### 1.1 Purpose

Symbolon is an authentication protocol in which login authority for an
application is held by an external **Vault**, not by the application
itself. The Vault issues short-lived, single-use, cryptographically
signed **Login Leases** that the application verifies before opening a
session.

### 1.2 Design goals

1. **Login is closed by default.** No standing login surface. The user
   must explicitly mint a lease for each session.
2. **No long-lived bearer credential ever reaches the application.**
   Each lease is one-time and bound to a fresh ephemeral keypair.
3. **The Vault cannot mint silently.** Every lease requires a fresh
   local user proof (biometric, PIN, or platform passkey) on the Vault
   device itself.
4. **The Verifier needs no network call to a central authority** to
   check a lease — only the Vault's published public key.
5. **Protocol is transport-agnostic.** Leases can travel over HTTP,
   QR, BLE, deep link, or USB.
6. **Spec is language-agnostic and small.** A correct verifier is
   implementable in ≤500 lines in any modern language.

### 1.3 Non-goals

- Symbolon is **not** an identity provider. It does not assert *who*
  the user is. Identity is proven to the Vault by other means (passkey,
  WebAuthn, biometric). Symbolon transports the assertion "the real
  user opened this door right now" to the application.
- Symbolon is **not** a session protocol. Once a lease is consumed,
  session management (TTL, refresh, revocation) is the application's
  responsibility.
- Symbolon does **not** replace TLS. It assumes the transport is
  already authenticated and confidential.

### 1.4 Terminology

| Term | Definition |
|---|---|
| **Vault** | A device (or hardware module) that holds a long-lived signing key and mints Login Leases after a fresh local user proof. |
| **Verifier** | The application (or its auth library) that accepts or rejects a Login Lease. |
| **Subject** | The human user the Vault is authenticating. |
| **Login Lease** | A signed object granting one-time login authority. Defined in §3. |
| **Ephemeral Keypair** | A keypair generated by the Vault for a single lease, used by the Subject's client device to answer the Verifier's challenge. |
| **JTI** | JSON Token Identifier — a globally unique ID for one lease. |
| **Consumed JTI** | A JTI the Verifier has recorded as used; reuse must fail. |
| **App ID** | A stable, Verifier-chosen string identifying the application. |
| **Vault Pubkey** | The Vault's long-lived Ed25519 public key, published via discovery (§7). |

### 1.5 Conformance keywords

The keywords **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and
**MAY** in this document are to be interpreted as described in RFC 2119
and RFC 8174.

## 2. Roles and trust model

```
   ┌─────────┐  (1) local user proof   ┌──────────┐
   │ Subject │──────────────────────▶ │  Vault   │
   └────┬────┘                        └────┬─────┘
        │                                  │
        │ (4) ephemeral keypair pubkey     │ (2) mint lease
        │     (Verifier's challenge)       │     (sign with vault key)
        ▼                                  ▼
   ┌──────────┐     (3) lease delivery     ┌─────────────┐
   │ Verifier │ ◀──────────────────────── │ Subject UA  │
   │ (the app)│                            └─────────────┘
   └──────────┘
        │
        │ (5) verify signature, replay, bindings
        ▼
     session
```

1. Subject proves themselves locally to the Vault (biometric/passkey/PIN).
2. Vault mints a lease, including a freshly generated **ephemeral
   keypair**. The lease is signed by the Vault's long-lived key.
3. The lease + ephemeral private key are delivered to the Subject's
   user-agent. Transport is out of scope here (§8 lists bindings).
4. The user-agent presents the lease to the Verifier and proves
   possession of the ephemeral private key by signing a Verifier-issued
   challenge.
5. Verifier validates the signature chain and starts a session.

### 2.1 What the Verifier trusts

- The Vault's published public key (obtained at enrollment time or via
  the discovery endpoint, §7).
- The integrity of its own clock (within `clock_skew_sec` tolerance).
- Its own record of consumed JTIs.

### 2.2 What the Verifier does NOT trust

- The user-agent. It is treated as a hostile carrier of the lease.
- The transport. TLS is assumed but not relied on for lease integrity.
- Anything signed by anyone other than the configured Vault key(s).

### 2.3 What the Vault MUST guarantee

- Its long-lived signing key never leaves a hardware-backed key store
  (secure enclave, TPM, HSM, or equivalent).
- A lease is minted ONLY after a fresh local user proof. Cached proofs
  MUST NOT be reused across leases.
- Each ephemeral keypair is generated fresh per lease. Reuse is a
  protocol violation.

## 3. Lease object

### 3.1 Structure

A Login Lease is a JSON object with the following fields. The signed
form is the JSON Canonicalization Scheme (JCS, RFC 8785) serialization
of this object, with the `vault_signature` field removed before signing
and reinserted after.

| Field | Type | Required | Description |
|---|---|---|---|
| `v` | integer | yes | Protocol version. **MUST** be `1` for this spec. |
| `type` | string | yes | **MUST** be `"symbolon.lease"`. |
| `jti` | string | yes | ULID or UUIDv7. Globally unique per Vault. |
| `vault_id` | string | yes | Stable Vault identifier (see §7). |
| `subject_id` | string | yes | Verifier-known Subject identifier. |
| `app_id` | string | yes | Verifier app identifier the lease is bound to. |
| `device_id` | string | yes | Subject user-agent device identifier. |
| `not_before` | string | yes | RFC 3339 timestamp (UTC, `Z` suffix). |
| `not_after` | string | yes | RFC 3339 timestamp (UTC, `Z` suffix). |
| `max_session_ttl_sec` | integer | yes | Hard cap for the session the Verifier creates. |
| `allowed_actions` | array of strings | yes | Action scope. May be `["*"]` for unrestricted. |
| `geo_constraint` | object | no | See §3.3. |
| `ephemeral_pubkey` | string | yes | Multibase-encoded Ed25519 public key. |
| `nonce_challenge_required` | boolean | yes | If `true`, Verifier **MUST** issue a challenge. |
| `extensions` | object | no | Implementation-defined. **MUST** be ignored if unknown. |
| `vault_signature` | string | yes | Multibase-encoded Ed25519 signature. |

### 3.2 Canonical example

```json
{
  "v": 1,
  "type": "symbolon.lease",
  "jti": "01JBYZK8R7E1Q3X9TWMV4PG2YH",
  "vault_id": "vault:01JBYZ...",
  "subject_id": "usr_01JBYZ...",
  "app_id": "xgs.admin",
  "device_id": "dev_01JBYZ...",
  "not_before": "2026-06-04T19:00:00Z",
  "not_after":  "2026-06-04T19:10:00Z",
  "max_session_ttl_sec": 1800,
  "allowed_actions": ["login","read","send"],
  "geo_constraint": {
    "countries": ["NL"],
    "asns": [1136, 33915]
  },
  "ephemeral_pubkey": "z6Mk...",
  "nonce_challenge_required": true,
  "vault_signature": "z3Ms..."
}
```

### 3.3 `geo_constraint`

```
{
  "countries": ["ISO-3166-1 alpha-2", ...],     // OR-matched
  "asns":      [integer, ...],                  // OR-matched
  "ip_cidrs":  ["1.2.3.0/24", ...]              // OR-matched
}
```

If `geo_constraint` is present, the Verifier **MUST** reject leases
whose request origin does not match at least one entry in **each**
non-empty subfield.

### 3.4 Signature

- Algorithm: **Ed25519** (RFC 8032). **MUST** be supported.
- Optional: `ecdsa-p256` for HSM compatibility. Signaled via the
  `extensions.sigalg` field.
- Signing input: JCS canonicalization (RFC 8785) of the lease object
  with `vault_signature` removed.
- Encoding: Multibase base58btc (`z` prefix) per W3C Multibase.

## 4. Verification algorithm

A conformant Verifier **MUST** execute the following steps in order.
Any failure **MUST** result in lease rejection. The Verifier **MUST
NOT** start a session on partial success.

```
verify(lease, request, config) :=
   1. parse lease as JSON; reject if malformed
   2. assert lease.v == 1
   3. assert lease.type == "symbolon.lease"
   4. lookup vault_pubkey for lease.vault_id in config.trusted_vaults
      reject if not found
   5. extract signature; JCS-canonicalize remaining fields
   6. verify Ed25519 signature; reject on failure
   7. assert lease.app_id == config.app_id
   8. assert now ∈ [lease.not_before − skew, lease.not_after + skew]
      where skew ≤ 30 seconds
   9. assert lease.jti NOT IN consumed_jti_store
       (atomic check-and-insert; see §4.1)
  10. if lease.geo_constraint present:
        assert request.origin matches geo_constraint per §3.3
  11. assert request.device_id == lease.device_id
  12. if lease.nonce_challenge_required:
        issue challenge = random_bytes(32)
        receive sig = client_sign(challenge, ephemeral_privkey)
        verify sig with lease.ephemeral_pubkey
        reject on failure
  13. mark lease.jti as consumed (durable)
  14. return session_authority {
        subject_id, app_id, allowed_actions,
        session_ttl = min(max_session_ttl_sec, config.app_max_ttl)
      }
```

### 4.1 Replay defence

The `consumed_jti_store` **MUST** support atomic check-and-insert.
A naive read-then-write is non-conformant — two concurrent verifications
of the same lease MUST NOT both succeed.

Recommended implementations:
- SQL: `INSERT INTO consumed_jti (jti, consumed_at) VALUES (...)` with
  a `PRIMARY KEY (jti)` constraint. Treat unique-violation as "already
  consumed".
- Redis: `SET jti 1 NX EX <ttl>` where `<ttl>` ≥ `not_after − now + skew`.

JTIs **MAY** be evicted from the store after `not_after + skew` has
passed, since further replays would already fail step 8.

### 4.2 Clock handling

- `clock_skew_sec` **MUST NOT** exceed 30. Verifiers **SHOULD** use 5.
- If the Verifier's clock cannot be trusted (no NTP, drifted), it
  **MUST** reject all leases rather than fall back to lease-internal
  time.

## 5. Vault obligations

### 5.1 Key management

- The Vault's long-lived signing key **MUST** be generated inside, and
  never exported from, a hardware-backed key store. Acceptable backings:
  iOS Secure Enclave, Android StrongBox / TEE, TPM 2.0, YubiHSM,
  AWS CloudHSM, Apple T2/M-series Secure Enclave.
- Software-only keys **MUST** be labeled as such in the Vault's
  discovery document (§7) and Verifiers **MAY** refuse them.

### 5.2 Local user proof

Before minting any lease, the Vault **MUST** obtain a fresh local
proof. Acceptable proofs:

- Platform biometric with liveness (Face ID, Touch ID, Android
  BiometricPrompt with `setConfirmationRequired(true)`).
- Platform PIN backed by the secure element.
- A WebAuthn `userVerification: "required"` ceremony against a
  platform authenticator.

Cached proofs (e.g. "trusted for 5 minutes") **MUST NOT** be reused
across leases. One proof = one lease.

### 5.3 Ephemeral keypair

The Vault **MUST** generate the lease's ephemeral keypair freshly per
lease. The ephemeral private key **MUST** be delivered only to the
Subject's authorized user-agent, never to the Verifier.

### 5.4 Audit log

The Vault **MUST** record an immutable, hash-chained audit entry per
lease minted, including: `jti`, `subject_id`, `app_id`, `device_id`,
timestamps, and the type of local user proof used. Recommended
construction: Ed25519-signed entries linked by SHA-256 `prev_hash`.

## 6. Error model

All errors are reported by the Verifier to the caller using the
following taxonomy. Numeric codes **MUST NOT** be reused across
versions.

| Code | Symbol | Meaning |
|---|---|---|
| 1001 | `lease_malformed` | JSON parse or schema failure. |
| 1002 | `lease_version_unsupported` | `v` field unknown. |
| 1003 | `lease_type_invalid` | `type` mismatch. |
| 1100 | `vault_unknown` | `vault_id` not in trusted list. |
| 1101 | `vault_software_only_refused` | Vault is software-only and policy forbids. |
| 1200 | `signature_invalid` | Ed25519 verification failed. |
| 1201 | `signature_alg_unsupported` | Non-Ed25519 algorithm not enabled. |
| 1300 | `lease_expired` | `now > not_after + skew`. |
| 1301 | `lease_not_yet_valid` | `now < not_before − skew`. |
| 1302 | `clock_untrusted` | Verifier refuses to assess time. |
| 1400 | `lease_replayed` | JTI already consumed. |
| 1500 | `app_mismatch` | `app_id` not for this Verifier. |
| 1501 | `device_mismatch` | `device_id` does not match request. |
| 1502 | `geo_constraint_failed` | Origin not in allowed geo/ASN/CIDR. |
| 1600 | `challenge_failed` | Ephemeral key signature invalid. |
| 1601 | `challenge_required_but_missing` | Verifier policy requires challenge. |
| 1700 | `consumed_store_unavailable` | Replay store offline; verifier MUST fail closed. |

Verifiers **SHOULD** return only the symbolic code to untrusted
callers, and log the full reason internally.

## 7. Discovery

Each Vault publishes a discovery document at a well-known URL.

```
GET https://<vault-host>/.well-known/symbolon-configuration
```

Response (JSON):

```json
{
  "vault_id": "vault:01JBYZ...",
  "spec_version": "1",
  "pubkey": "z6Mk...",
  "sigalg": ["ed25519"],
  "key_backing": "hardware",
  "attestation": {
    "type": "apple-anonymous" | "android-key" | "tpm-2.0" | "none",
    "document": "base64..."
  },
  "issued_at": "2026-06-04T00:00:00Z",
  "rotation_policy_days": 365
}
```

Verifiers **SHOULD** cache the discovery document and refresh it at
most every 24 hours unless a `vault_unknown` error is returned for a
known `vault_id` (key rotation hint).

For local/offline vaults (e.g. a mobile app paired out-of-band), the
discovery document **MAY** be exchanged directly during enrollment and
never fetched over the network.

## 8. Transport bindings

The protocol does not mandate a single transport. The following
bindings are defined.

### 8.1 HTTP header binding

Subject's user-agent presents the lease in a request header:

```
Authorization: Symbolon <base64url(lease_json)>
Symbolon-Challenge-Response: <base64url(ed25519_sig)>
```

The challenge response is computed over the Verifier's challenge,
delivered via a prior `WWW-Authenticate: Symbolon challenge="..."`
response.

### 8.2 QR / deep-link binding

Used for cross-device flows (Vault on phone, Verifier on laptop).

QR payload (text):

```
symbolon://lease?d=<base64url(lease_json)>&c=<callback_url>
```

The Vault scans/generates the QR; the user-agent on the target device
POSTs the lease to `<callback_url>`.

### 8.3 BLE binding

Out of scope for v0.1. Reserved.

### 8.4 USB / HID binding

Out of scope for v0.1. Reserved.

## 9. Security considerations

### 9.1 Threat model

Symbolon is designed against:

- Stolen bearer tokens — leases are one-time and ephemeral-key bound.
- Stolen Vault — local user proof per lease defeats passive theft.
- Compromised user-agent — agent cannot reuse a lease past `not_after`,
  cannot use it from a different `device_id`, and cannot forge new ones.
- Verifier breach — the Verifier holds no long-term auth material; an
  attacker who dumps the Verifier database gets only consumed-JTI
  records.

Symbolon does NOT defend against:

- A user who voluntarily approves a malicious lease.
- A fully compromised Vault device whose secure-enclave key has been
  extracted (assumed infeasible per §5.1).
- Out-of-band session hijack after a valid login (the Verifier's
  session layer must defend this — see DPoP, mTLS, etc.).
- Coercion of the user. Mitigation: panic-lock (§10.3).

### 9.2 Cryptographic agility

Ed25519 is mandatory. Future versions **MAY** add PQC suites
(ML-DSA / Dilithium). The `extensions.sigalg` field reserves the path.
Until v2.0, Verifiers **MUST** reject non-Ed25519 signatures unless
explicitly enabled in config.

### 9.3 Clock-skew abuse

A Verifier with a fast clock could prematurely expire leases (denial of
service). A Verifier with a slow clock could honor expired leases.
Verifiers **MUST** use a trusted NTP source and **MUST** fail closed if
the source is unreachable.

### 9.4 JTI collision

JTIs are required to be ULID or UUIDv7. Random collisions are
astronomically unlikely; a Vault that emits colliding JTIs is
non-conformant and **MUST** be revoked.

### 9.5 Long leases

Verifiers **SHOULD** reject leases with `not_after − not_before > 3600`
(1 hour). Short-lived leases are the whole point.

## 10. Optional features

### 10.1 Action binding

`allowed_actions` constrains what the resulting session may do. The
Verifier **MUST** enforce this at the action boundary, not only at
session creation.

Example: a lease with `allowed_actions: ["read"]` **MUST NOT** be
upgraded to write access by any in-session privilege escalation. A
write requires a new lease.

### 10.2 Transaction signing

For high-risk actions, the Vault **MAY** mint a single-action lease
(`allowed_actions: ["delete_server:srv_123"]`, `not_after − not_before
≤ 60s`) that the Verifier requires in addition to the session.

### 10.3 Panic lock

The Vault **MAY** expose a panic-lock that:

- Revokes all outstanding leases by publishing a `revocation_epoch`
  bump in the discovery document.
- Refuses to mint new leases for a configurable cooldown.

Verifiers **MUST** treat any lease with `issued_at <
vault.revocation_epoch` as `signature_invalid` (1200).

### 10.4 Break-glass capsule

A pre-sealed, offline lease with extended `not_after` and
`allowed_actions: ["recovery"]`, gated by external quorum + delay.
Implementation-defined; out of normative scope for v0.1.

## 11. Conformance

### 11.1 Verifier conformance

A conformant Verifier **MUST**:

1. Implement §4 verification in the specified order.
2. Provide atomic JTI replay defence per §4.1.
3. Support Ed25519 signatures.
4. Use clock skew ≤ 30 seconds.
5. Return errors per §6.
6. Fail closed on any unrecoverable internal error.

### 11.2 Vault conformance

A conformant Vault **MUST**:

1. Hold its signing key in a hardware-backed store (or label
   software-only per §5.1).
2. Require a fresh local user proof per lease (§5.2).
3. Generate fresh ephemeral keypairs per lease (§5.3).
4. Maintain a hash-chained audit log (§5.4).
5. Publish a discovery document per §7.

### 11.3 Test vectors

A normative set of test vectors will accompany the v1.0 freeze. Draft
vectors are provided in `symbolon-test-vectors-v0.1.json` (TBD).

A conformant implementation **MUST** pass all vectors marked `MUST`.

## 13. Open questions (to resolve before v1.0)

1. **Trademark + domain clearance for "Symbolon".** Etymologically
   exact (Greek for the broken-token identity proof — see project
   README), but USPTO/EUIPO class 9/42 search and domain availability
   (`symbolon.dev`, `.org`, `.io`) still need confirmation before v1.0
   freeze. Fallbacks: Synthema, Halvsign, Brevia.
2. **Multi-Vault enrollment.** How does a Subject enroll a second Vault
   for redundancy without a central directory? Out-of-band QR pairing
   is the leading proposal.
3. **Session-layer integration.** Should the spec include a non-
   normative appendix on DPoP / mTLS / cookie binding? Leaning yes.
4. **Recovery.** Vault loss is a UX cliff. Recovery model is currently
   out of scope; consider an appendix on quorum recovery.
5. **Privacy.** `subject_id` and `device_id` leak across Verifiers if
   reused. Recommend per-Verifier pairwise IDs (à la OIDC pairwise).
6. **PQC roadmap.** When to add ML-DSA. Ed25519-only is reasonable for
   v1.0 but a public roadmap reduces adopter anxiety.
7. **Attestation format.** Reusing WebAuthn FIDO MDS vs. defining our
   own. Reusing FIDO MDS is the right answer if practical.

## Appendix A — Minimal verifier pseudocode

```python
def verify(lease_bytes, request, config) -> SessionAuthority:
    lease = json.loads(lease_bytes)
    require(lease["v"] == 1,        ERR.lease_version_unsupported)
    require(lease["type"] == "symbolon.lease", ERR.lease_type_invalid)

    vault = config.trusted_vaults.get(lease["vault_id"])
    require(vault is not None,      ERR.vault_unknown)

    sig = multibase_decode(lease.pop("vault_signature"))
    msg = jcs_canonicalize(lease)
    require(ed25519_verify(vault.pubkey, msg, sig), ERR.signature_invalid)

    now = trusted_now()
    require(now >= iso(lease["not_before"]) - SKEW, ERR.lease_not_yet_valid)
    require(now <= iso(lease["not_after"])  + SKEW, ERR.lease_expired)

    require(lease["app_id"] == config.app_id, ERR.app_mismatch)
    require(lease["device_id"] == request.device_id, ERR.device_mismatch)

    if "geo_constraint" in lease:
        require(geo_match(request.origin, lease["geo_constraint"]),
                ERR.geo_constraint_failed)

    require(consumed_store.insert_unique(lease["jti"], lease["not_after"]),
            ERR.lease_replayed)

    if lease["nonce_challenge_required"]:
        challenge = os.urandom(32)
        sig = request.client_sign(challenge)
        require(ed25519_verify(multibase_decode(lease["ephemeral_pubkey"]),
                               challenge, sig),
                ERR.challenge_failed)

    return SessionAuthority(
        subject_id      = lease["subject_id"],
        app_id          = lease["app_id"],
        allowed_actions = lease["allowed_actions"],
        session_ttl     = min(lease["max_session_ttl_sec"], config.app_max_ttl),
    )
```
